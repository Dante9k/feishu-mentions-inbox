# 多维表格配置

[返回 README](../README.md) · [飞书应用配置](feishu-setup.md) · [验收清单](acceptance-checklist.md)

必须创建一份“独立多维表格”，不能使用嵌入飞书文档或电子表格的 Base，因为后两者不支持高级权限。把该 Base 的 `app_token` 和四个 `table_id` 写入 `.env`。

## 1. 数据表和字段

字段名称必须与下表完全一致，后端按名称写入。

### 个人 @收件箱

| 字段 | 类型 | 员工权限 |
|---|---|---|
| 目标用户 | 成员（多选关闭） | 只读，行筛选依据 |
| 群名、发送人、正文、消息类型、定位信息 | 文本 | 只读 |
| 提及类型 | 单选：直接@我、@所有人 | 只读 |
| 发送时间、处理时间 | 日期时间 | 只读 |
| 处理状态 | 单选：待处理、处理中、已处理、忽略 | 可编辑 |
| 处理备注 | 多行文本 | 可编辑 |
| 源状态 | 单选：有效、已撤回 | 只读 |
| 内部待办ID、源消息ID、目标用户ID | 文本 | 隐藏、只读 |
| 版本 | 数字（整数） | 隐藏、只读 |
| 表格修改时间 | 最后修改时间（系统字段） | 隐藏、只读 |

### 个人设置

| 字段 | 类型 |
|---|---|
| 用户 | 成员（多选关闭） |
| 包含@所有人 | 复选框 |
| 授权状态 | 单选：待授权、已授权 |
| 群覆盖率 | 百分比 |
| 已覆盖群数、目标群数 | 数字 |
| 最后检查时间 | 日期时间 |
| 内部用户ID | 文本 |

### 群覆盖管理

字段：用户（成员）、用户姓名（文本）、群名（文本）、群ID（文本）、是否内部群（复选框）、机器人在群（复选框）、覆盖状态（单选）、处理建议（文本）、最后检查时间（日期时间）、内部用户ID（文本）。

### 启用用户管理

字段：用户（成员）、姓名（文本）、内部用户ID（文本）、启用（复选框）、启用状态（单选：已启用、已停用）、授权状态（单选）、包含@所有人（复选框）。管理员添加新行时选择“用户”并勾选“启用”。

## 2. 高级权限

开启高级权限，创建一个“普通员工”自定义角色，并将其 `role_id` 写入 `BITABLE_USER_ROLE_ID`。应用还必须有编辑和管理该 Base 的权限，否则高级权限开启后 API 会拒绝写入。

普通员工角色规则：

- “个人 @收件箱”：仅可查看 `目标用户` 包含当前访问者的记录；仅“处理状态”和“处理备注”可编辑。
- “个人设置”：仅可查看 `用户` 为当前访问者的记录；仅“包含@所有人”可编辑。
- “群覆盖管理”和“启用用户管理”：不可查看。
- 不允许员工创建、删除、导出记录或修改视图、字段、自动化。

员工 OAuth 成功后，服务会先把该员工以 `view` 权限加入文档协作者，再加入“普通员工”自定义角色。自定义角色优先于系统阅读者。停用时两层权限都会移除。

不要把普通员工额外加入“管理员”角色，也不要加入其他可查看全量行的自定义角色。一个自定义角色最多支持 200 名协作者；当前 100–200 人名单必须保留容量余量。

## 3. 自动化回调

三个自动化都使用 HTTPS POST，并添加请求头：

```text
Authorization: Bearer <BITABLE_CALLBACK_TOKEN>
Content-Type: application/json
```

状态自动化：当“处理状态”或“处理备注”变化时调用 `/integrations/bitable/status`：

```json
{
  "item_id": "{{内部待办ID}}",
  "record_id": "{{当前记录ID}}",
  "status": "{{处理状态}}",
  "note": "{{处理备注}}",
  "version": 1,
  "changed_at": 1787673600000
}
```

其中 `version` 使用当前行“版本”字段的动态值，`changed_at` 使用“表格修改时间”的毫秒时间戳，两者都不要固定写示例值。后端以版本和修改时间解决重复、乱序请求；后端投影再次触发自动化时，相同状态/备注会幂等成功，不会形成同步循环。

设置自动化：仅当“包含@所有人”变化时调用 `/integrations/bitable/settings`：

```json
{
  "user_id": "{{内部用户ID}}",
  "record_id": "{{当前记录ID}}",
  "include_at_all": true
}
```

布尔值使用复选框的动态值。

启用名单自动化：仅管理员可编辑。当“启用”变化或新建包含“用户”的记录时调用 `/integrations/bitable/users`：

```json
{
  "enabled": true,
  "record_id": "{{当前记录ID}}",
  "open_id": "{{用户字段中的 Open ID}}",
  "name": "{{用户显示名}}",
  "send_activation_message": true
}
```

后端会从通讯录把 `open_id` 换成稳定 `user_id`。已处于相同启用状态时按幂等成功处理，不重复发送邀请，不触发回写循环。

## 4. 上线前权限门禁

必须用管理员、员工 A、员工 B 三个真实账号验证：

- A 无法查看、搜索、导出或修改 B 的收件箱和设置记录。
- A 只能改自己的状态、备注和 `@所有人` 开关，不能改正文、目标用户、内部 ID 或版本。
- B 的处理动作不影响 A 的同源待办。
- 管理表对 A/B 完全不可见；管理员可见全量这一阶段性限制已被业务接受。

任一项失败都不得进入部门试运行。
